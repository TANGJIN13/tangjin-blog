## 日常用法

### 方式一：网页后台（不用碰命令行）

1. 打开 https://tangjin.xyz/admin/
2. 首次使用点 **⚙️ 设置**，填入 GitHub Token
3. 点 **+ 新建文章** → 填标题/描述/标签 → 写正文
4. 点 **🚀 发布** → 等 1-2 分钟自动上线

**Token 怎么来**：https://github.com/settings/tokens
- 建议选 Fine-grained token
- 只需要 `tangjin-blog` 这一个仓库的 **Contents: Read and write**
- Token 存在浏览器 localStorage，不上传任何服务器

### 方式二：本地写 Markdown + 一键推送

```bash
# 1. 在 src/content/posts/ 里新建 .md 文件
# 2. 双击 push.cmd（自动提交 + 同步 + 推送）
```

`push.cmd` 会做四件事：
1. 检测网络（直连不通就自动走本地代理 127.0.0.1:7897）
2. 提交本地改动
3. `git pull --rebase` 同步远程（避免被拒绝）
4. 推送

> 代理端口不是 7897 的话，改 `push.ps1` 里的 `$ProxyPort`。

### 方式三：绕过 GitHub，直接传服务器

```bash
# 双击 deploy.cmd
```

本地构建后直接 scp 到服务器，**不走 GitHub、不触发 Actions**。
适合只想快速看效果、不想等 CI 的场景。

## 安全模型

### 后台为什么不是「人人可上传」

`/admin/` 是**纯静态 HTML**，服务器上**没有任何接收上传的后端**。

它的工作方式是：在你自己的浏览器里存 GitHub Token，点发布时**从浏览器直接调 GitHub API**。
别人打开页面时 localStorage 是空的，没有 Token，GitHub 直接返回 `401`。

实测结果：

| 测试 | 结果 |
|---|---|
| 不带凭证往仓库写文件 | `401` 拒绝 |
| 用假 Token 写文件 | `401` 拒绝 |
| 匿名访问仓库 | `404`（私有仓库） |

### 已有的两层加固

**第一层：`/admin/` 加 HTTP Basic 认证**

```
用户名：tj
密码：  见你自己保存的记录（部署时由管理员设置）
```

配置位置：
- `/etc/nginx/.htpasswd-admin` — 密码文件（`root:www-data` 640）
- `/etc/nginx/snippets/admin-auth.conf` — 认证配置片段
- `/etc/nginx/sites-available/blog` — 在 443 块里 `include` 该片段

效果：无凭证 `401`，错误密码 `401`，正确密码 `200`；其他页面不受影响。

**第二层：部署密钥限制为 rrsync 只写**

`~/.ssh/authorized_keys` 里部署密钥那行被加了强制命令：

```
command="/usr/bin/rrsync -wo /var/www/blog",restrict ssh-ed25519 AAAA... github-actions-deploy@tangjin.xyz
```

实测限制效果：

| 尝试 | 结果 |
|---|---|
| 执行 `whoami` / `cat /etc/passwd` | ❌ `SSH_ORIGINAL_COMMAND does not run rsync` |
| rsync 写入 `/var/www/blog` | ✅ 成功 |
| 写到目录外（`/../etc/`） | ❌ `do not use .. in arg` |
| 读取站点文件 | ❌ `reading from write-only server is not allowed` |

**这意味着：即使 GitHub 上的私钥泄露，攻击者也只能往站点目录写文件，拿不到 shell、用不了 sudo、读不了其他数据。**

### 攻击链被封堵的对比

```
加固前：Token 泄露 → 改工作流打印私钥 → SSH 登录 → 免密 sudo → root
加固后：Token 泄露 → 改工作流打印私钥 → 只能 rrsync 写 /var/www/blog
                                      → 不能执行命令、不能 sudo、不能读文件
```

### 仍然需要注意的

1. **Token 权限最小化**：GitHub Token 用 Fine-grained，只给 `tangjin-blog` 这一个仓库的
   `Contents: Read and write`，并设置有效期。不要给 `repo` 全权限或管理员权限。
2. **`--delete` 的危险性**：部署用的 `rsync --delete` 会清理目标目录里多余的旧文件。
   因为目标被 rrsync 锁死在 `/var/www/blog`，所以只影响站点目录。
   **但手动执行 rsync 时务必确认路径**，写错会清空站点。
3. **本机私钥备份**：`deploy-key/github-actions-deploy` 那份是备份。
   泄露的话删掉服务器 `~/.ssh/authorized_keys` 里对应那行即可失效。

### 修改后台密码

```bash
# 在服务器上（把 新密码 换成你要的）
HASH=$(openssl passwd -apr1 '新密码')
sudo sh -c "printf 'tj:%s\n' '$HASH' > /etc/nginx/.htpasswd-admin"
sudo chmod 640 /etc/nginx/.htpasswd-admin
sudo chown root:www-data /etc/nginx/.htpasswd-admin
sudo systemctl reload nginx
```

### 紧急：私钥泄露了怎么办

```bash
# 1. 服务器上删掉部署密钥那一行
ssh tangjin "sed -i '/github-actions-deploy/d' ~/.ssh/authorized_keys"

# 2. 本地重新生成一对，公钥加回服务器
python ops/... # 或用 ssh-keygen 手动生成

# 3. 更新 GitHub Secret（仓库 Settings → Secrets → SSH_PRIVATE_KEY）
```

## 出问题排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 页面 403 | 目录权限不是 755 | 服务器执行 `find /var/www/blog -type d -exec chmod 755 {} +` |
| push 报 `non-fast-forward` | 本地没拉远程（后台发过文章） | 用 `push.cmd`，它会自动 pull |
| push 报 `Connection was reset` | 直连被墙 | 启动代理，或确认 `push.ps1` 里端口对 |
| Actions 报错 `SSH_PRIVATE_KEY` | Secret 没配 | 见下方「密钥信息」 |
| admin 发布报 401 | Token 过期 | 重新生成 |
| admin 发布报 404 | 仓库名填错 | 后台设置里改 |
| 改了没生效 | Actions 还在跑 | 去 Actions 页面看进度 |

**查看构建进度**：https://github.com/TANGJIN13/tangjin-blog/actions

## 一次性配置记录（已完成，仅供追溯）

如果将来要重建，需要做这些：

1. **服务器目录权限**：`chown -R ubuntu:www-data /var/www/blog`，目录 755 / 文件 644
   - ⚠️ Windows 的 `scp` 上传目录会建成 700，nginx 读不到 → 必须显式 chmod
2. **生成部署密钥**：`ssh-keygen -t ed25519`，公钥追加到服务器 `~/.ssh/authorized_keys`
3. **GitHub Secret**：把私钥全文写入 `SSH_PRIVATE_KEY`
4. **Actions 工作流**：`.github/workflows/deploy.yml`（构建 + rsync + 权限校验 + 线上探测）

这些都已落地，相关脚本在 `ops/` 目录。
